Challenge Description:

The challenge, Not Under the Mat, was a 200-point reverse-engineering challenge. The prompt explained that the McCallisters' spare key was no longer hidden under the doormat. Instead, the key had been replaced by an executable file that was taken along with the rest of the information collected by a stealer. The goal was to locate the program and work out how it opens the McCallisters' door.

The challenge also gave an important hint: there was no infrastructure or external service to investigate. Everything needed for the challenge was contained in the stealer-log ZIP attached to Gold Star Student.



My Actions / Solution:

I started by locating the executable provided for the challenge, unlock-door.exe. Since this was an unknown Windows executable, I did not immediately run it. I wanted to inspect its contents first and see whether it contained useful strings, configuration values, or other information that could explain what the program did.

File Analyzed: unlock-door.exe
File Size: 1,340,928 bytes

1. Converting the executable into a Hexdump with CyberChef

I opened CyberChef and loaded unlock-door.exe into the Input pane. Since an executable is binary data, viewing it directly as text would not be very useful. I searched the Operations list for To Hexdump and added that operation to the Recipe pane.

CyberChef converted the executable into a hexadecimal dump. The dump displays the file offset, the bytes in hexadecimal, and an ASCII representation of printable characters. That ASCII column is especially useful because it can expose readable strings that are embedded in the executable.

I copied/exported the resulting dump and saved it as exe_hex.txt so I could search through it without having to repeatedly load the original executable.



2. Identifying the executable

Before looking for the challenge-specific information, I checked the beginning of the dump. The first two bytes were 4D 5A, which translate to the ASCII characters MZ. This is the standard DOS header signature found at the beginning of a Windows Portable Executable (PE) file. The PE signature itself is 50 45 00 00 (PE\0\0).

I also checked the file metadata from the terminal:

Command Ran: file unlock-door.exe

PE32+ executable for MS Windows 6.01 (console), x86-64, 8 sections

This confirmed that the file was a 64-bit Windows console executable. I then checked its Go build metadata:

Command Ran: go version -m unlock-door.exe

go1.22.3
GOOS=windows
GOARCH=amd64
CGO_ENABLED=0

This showed that the executable had been built with Go 1.22.3 for Windows on the AMD64 architecture. Knowing that it was a Go binary helped explain why the dump contained a large amount of runtime and standard-library text mixed in with the program's own strings.



3. Searching the Hexdump for useful strings

With the hexdump available, I started looking through the ASCII column for terms related to the challenge, including door, unlock, code, service, and McCallister. This helped separate the application's information from the large amount of unrelated Go runtime strings.

One of the first useful strings identified the program: 

LockMaster SL-500 Service Utility v2.4.1
Site: McCallister residence, Winnetka IL

This tied the executable directly to the McCallister residence mentioned in the challenge. The dump also contained a usage message: 

usage: unlock-door.exe --code <service code>

This revealed that the program expects a service code supplied through the --code command-line argument. I also found messages indicating what happens when the code is accepted or rejected: 

[+] service code accepted
[-] service code rejected, lock stays engaged
[+] front door: UNLOCKED

These strings describe the application's success and failure paths. They indicate that the program checks a supplied service code and has a success path that reports the front door as unlocked.

4. Finding the service-code clue

While searching through the dump, I also came across the string KEVIN-PIN-IS-1337. This stood out because the program's usage message showed that it required a service code. The value is embedded in the executable's string data, making it a strong candidate for the code expected by the utility.

The relevant value appears in the surrounding text as part of a Go runtime GODEBUG string. Based on the challenge context and the executable's command-line usage, I treated it as a service-code clue rather than assuming it was independently verified. The likely test command would be: 

unlock-door.exe --code KEVIN-PIN-IS-1337

I did not rely on executing the binary to recover the flag. The static evidence was enough to identify the encoded flag in the next step.

5. Locating the encoded flag

Continuing through the hexdump, I found a long string that did not look like ordinary text: 

ZmxhcmV7dGgzX2JhbmQxdHNfdW5sMGNrM2RfdGgzX2QwMHJ9

This string uses the Base64 character set and was a good candidate for an encoded value. Its location in the dump was around offset 0xAE37D. Rather than trying to interpret it manually, I copied the complete value so it could be decoded.

6. Decoding the Base64 value in CyberChef

I returned to CyberChef and pasted the encoded string into the Input pane. I then searched for the From Base64 operation and added it to the Recipe pane. CyberChef decoded the input and displayed the resulting text in the Output pane.



The decoded output was: 

flare{th3_band1ts_unl0ck3d_th3_d00r}

This matched the flag format supplied in the challenge description, confirming that the encoded string contained the flag.

7. Verifying the flag

To make sure that the value had been decoded correctly, I encoded the recovered flag back into Base64 using Python: 

import base64

flag = "flare{th3_band1ts_unl0ck3d_th3_d00r}"

encoded = base64.b64encode(flag.encode()).decode()

print(encoded)

The output was the exact same Base64 string that I had found in the executable: 

ZmxhcmV7dGgzX2JhbmQxdHNfdW5sMGNrM2RfdGgzX2QwMHJ9

Matching the original value confirmed that the decoding process was correct and that the flag had not been changed during extraction.

8. Final file verification

As a final forensic check, I calculated the SHA-256 hash of the executable so that the exact file used during the analysis could be identified:

Command Ran: sha256sum unlock-door.exe

90ddd81ac86701faa26f9c240bf0bbbf1e0cb515af7e43687cd795a543496a0b

Found Flag:

flare{th3_band1ts_unl0ck3d_th3_d00r}

Conclusion:

This challenge was solved by statically analyzing the supplied Windows executable rather than running an unknown program. I first converted unlock-door.exe into a hexdump using CyberChef's To Hexdump operation and saved the result as exe_hex.txt. I then searched the readable ASCII portion of the dump for strings that related to the challenge, which revealed the LockMaster utility, its expected --code argument, and its door-unlocking messages.

The most important discovery was a Base64-encoded string embedded in the executable. Using CyberChef's From Base64 operation, I decoded the value and recovered the flag. I then re-encoded the flag with Python to verify that it matched the original string found in the dump.

This challenge was a good example of how useful a hexdump can be when investigating an unknown executable. Even without source code, the combination of file identification, readable-string analysis, and decoding helped reveal both the program's intended purpose and the flag.
